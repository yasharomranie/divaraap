# به‌روزرسانی از پنل و دارایی‌های محلی

در بستهٔ جدید، مدیریت ← تنظیمات ← به‌روزرسانی سایت مسیر معمول انتشار نسخه است. یک بار مخزن `owner/name`، شاخهٔ `main` و برای مخزن خصوصی توکن fine-grained با Contents: Read-only را ذخیره کنید. توکن با رمزنگاری Spatie Settings و APP_KEY ذخیره می‌شود؛ در بازکردن مجدد فرم به مرورگر برنمی‌گردد. خالی‌گذاشتن فیلد، توکن قبلی را حفظ می‌کند. تغییر APP_KEY بدون انتقال کلید قدیمی، توکن‌ها و سایر داده‌های رمزنگاری‌شده را از دسترس خارج می‌کند.

قبل از اولین ارتقا «ساخت کد بازیابی» را بزنید و کد را خارج از هاست نگه دارید. کد جدید قبلی را باطل می‌کند. سپس تنظیمات ذخیره‌شده را بررسی و «دریافت و نصب آخرین نسخه» را انتخاب کنید. هنگام آماده‌سازی و نصب صفحه را نبندید. بعد از موفقیت لینک ورود به نسخهٔ جدید نمایش داده می‌شود.

## آماده‌سازی در گیت‌هاب

Workflow `.github/workflows/shared-release.yml` پس از push به main، کتابخانه‌های تولید Composer، فایل‌های Vite، دارایی‌های Filament و تصاویر تلفن را در GitHub Actions آماده می‌کند و `divaraap-update.zip` و نسخهٔ عمومی نصاب را به release با تگ `deploy-main` می‌فرستد. Actions باید روی مخزن فعال و مجاز به نوشتن Contents باشد. پیش از اولین کلیک در سایت، اجرای سبز این workflow و وجود فایل انتشار را بررسی کنید. تغییر شاخه در فرم به انتشار متناظر `deploy-BRANCH` نیاز دارد؛ workflow فعلی فقط main را منتشر می‌کند. نام شاخهٔ این قابلیت فعلاً فقط حروف لاتین، رقم، نقطه، خط تیره و زیرخط می‌پذیرد.

نسخهٔ اختصاصی نصاب اولیه حاوی کد نصب خصوصی است و به release عمومی فرستاده نمی‌شود. نسخهٔ عمومی نصاب با حذف INSTALLATION-CODE.txt و divaraap/install.token منتشر می‌شود؛ مالک قبل از نصب، با CREATE-INSTALLATION-KEY.html آفلاین کد تازه و فایل هش را تولید و فایل install.token را از File Manager در مسیر خصوصی برنامه قرار می‌دهد. ZIP سورس خام مخزن، بستهٔ ارتقا نیست و پذیرفته نمی‌شود؛ سورس خام vendor و build لازم را ندارد. SHA-256 فایل ارتقا با digest اعلام‌شدهٔ API گیت‌هاب مقایسه می‌شود. توکن دانلود هنگام انتقال به دامنهٔ فایل‌های گیت‌هاب ارسال نمی‌شود و مقصدهای دلخواه پذیرفته نمی‌شوند.

## چیدمان امن نسخه‌ها

کد اولیه در Home/divaraap حفظ می‌شود. کدهای ارتقا در divaraap/releases/ID و فایل‌های ایستای هر نسخه در public_html/_releases/ID قرار می‌گیرند. فایل active-release.json به‌صورت اتمی تعویض می‌شود؛ دانلود و استخراج روی نسخهٔ فعال انجام نمی‌شود. .env، APP_KEY، storage، آپلودها، installed.lock، فایل‌های بازیابی و ورودی‌های ثابت وب از ZIP ارتقا جایگزین نمی‌شوند. فایل PHP از ZIP ارتقا وارد مسیر عمومی نمی‌شود. نسخهٔ فعال و قبلی برای برگشت حفظ می‌شوند؛ در آماده‌سازی بعدی نسخه‌های بلااستفاده پاک می‌شوند. پشتیبان‌های SQL خودکار پاک نمی‌شوند و باید دوره‌ای آرشیو شوند.

نصب با یک عمل در پنل انجام می‌شود، اما مرورگر پس از آماده‌سازی خودکار درخواست دوم به runner مستقل می‌زند تا Laravel و کتابخانه‌های نسخهٔ جدید در یک پردازش تازه بارگذاری شوند. Cron، SSH، git، Composer، npm و اجرای shell روی هاست استفاده نمی‌شود. برای ارتقا اتصال خروجی HTTPS هاست به api.github.com و release-assets.githubusercontent.com لازم است. محدودیت سخت زمان وب‌سرور با PHP قابل تضمین یا حذف نیست؛ قطع پاسخ را معادل موفقیت نصب ندانید و ابتدا وضعیت سایت و بازیابی را بررسی کنید.

## پشتیبان و شکست نصب

runner سایت را موقتاً 503 می‌کند، از جدول‌های InnoDB در MySQL/MariaDB پشتیبان SQL خصوصی می‌گیرد، مهاجرت‌های دیتابیس و settings را اجرا می‌کند و کش‌های تنظیمات، مسیرها و نماها را بازسازی می‌کند. جدول‌های دارای ستون generated نیز پشتیبانی می‌شوند. دیتابیس دارای view، trigger یا جدول غیر InnoDB قبل از مهاجرت رد می‌شود. مرحله، خروجی فرمان و خطای نصب در deployment-job.json خصوصی ثبت می‌شود.

اگر آماده‌سازی شکست بخورد، نسخهٔ فعال عوض نمی‌شود. اگر مهاجرت SQL خطا بدهد، احتمال تغییر بخشی از دیتابیس وجود دارد و حالت 503 باقی می‌ماند. صفحهٔ مستقل `/recover.php` حتی بدون بالا آمدن Laravel کار می‌کند: با کد بازیابی می‌توان نسخهٔ فعال فعلی یا کد قبلی را فعال و حالت نگهداری را برداشت. برگشت کد، دیتابیس را برنمی‌گرداند. مهاجرت‌های محصول باید با نسخهٔ قبل سازگار باشند. در تغییر مخرب یا شکست DDL، بازگردانی دیتابیس از فایل divaraap/deployments/ID.sql به دیتابیس خالی با ابزار مدیریت هاست لازم است؛ هیچ دادهٔ کاربر خودکار حذف نمی‌شود. بازیابی SQL در دیتابیس آزمایشی جدا بررسی شده است.

فایل‌های ثابت index.php، deployment-runner.php و recover.php در ارتقا تعویض نمی‌شوند؛ تغییر پروتکل این ورودی‌ها به بسته و انتقال کنترل‌شدهٔ جدید نیاز دارد. چیدمان فعلی مخصوص document root برابر Home/public_html است. برای addon domain چیدمان باید پیش از نصب تنظیم و آزمایش شود. PHP باید حداقل ۱٫۸ گیگابایت فضای خالی برای هر آماده‌سازی و اجازهٔ نوشتن در پوشهٔ نسخه‌ها و دارایی‌ها داشته باشد؛ فضای لازم برای پشتیبان دیتابیس جداست.

## بدون CDN

فونت وزیرمتن، JS، CSS، تصاویر تلفن و کتابخانه‌های مرورگر از همان دامنه بارگذاری می‌شوند و vendor در بسته وجود دارد. کشور تلفن محلی انتخاب می‌شود و lookup خارجی IP غیرفعال است. prepare-local-assets.py تصاویر تلفن را از پکیج نصب‌شده کپی، آدرس CSS آن‌ها را نسبت به همان نسخه اصلاح و ارجاع خارجی CSS را رد می‌کند. اسکریپت و CSS و فونت خارجی در پروفایل shared با CSP مسدودند. Alpine/Livewire همچنان برای عملکرد فعلی به inline/eval مجاز نیاز دارند؛ این سیاست معادل CSP سخت بدون inline نیست.

نقشهٔ گوگل و Turnstile سرویس خارجی‌اند و اسکریپت آن‌ها در این حالت مجاز نیست؛ برای محصول با دارایی کاملاً محلی فعالشان نکنید. ایمیل، پرداخت، ورود اجتماعی و دانلود ارتقا نیز در صورت استفاده به سرویس مربوط نیاز دارند؛ محلی‌بودن کتابخانه‌ها این ارتباط‌ها را آفلاین نمی‌کند. تصاویر خارجی دلخواهِ محتوای کاربر با کتابخانهٔ CDN یکسان نیستند.
